# ADR-0081 — `ConsumerEventListener` parity (becameActive/becameInactive)

- **Status**: Accepted
- **Date**: 2026-07-17
- **Decider**: Florentin Dubois
- **Tags**: consumer, failover, push-delivery, parity, runtime, sans-io

## Context

The Java client's `Failover` subscription notifies application code of active/standby transitions via `ConsumerBuilder#consumerEventListener(ConsumerEventListener)`, whose `becameActive(Consumer, int partitionId)` / `becameInactive(Consumer, int partitionId)` callbacks fire whenever the broker sends `CommandActiveConsumerChange`.
magnetar's sans-io `Connection` already parses that command (issue #307 added the failover-reflow gate that re-arms flow on promotion) and surfaces a `ConnectionEvent::ActiveConsumerChanged` — but nothing in the runtime engines or façade turned that into a durable, pollable per-consumer state or a push callback.
A consumer had no way to ask "am I active right now?" or to be notified the next time that changes; the only trace was one entry in the connection-wide event queue, easy to miss between polls and never drained by either driver, so it accumulated unbounded in the proto queue under a chatty broker.

This sits directly beside [ADR-0064](0064-consumer-message-listener-push-delivery.md)'s push-delivery precedent: the architectural shape (a `tokio::spawn`ed poller over an engine-generic `ConsumerApi` future, no channel, no proto-side callback) is identical, just aimed at a different signal — the active/standby transition instead of message delivery. The #307 reflow gate also lives in the same code path (the `ActiveConsumerChange` arm's per-slot lock), so unlike ADR-0064 this feature IS a `magnetar-proto` change: the reflow predicate and the new state-recording had to land under the exact same lock acquisition (ADR-0038) rather than compose two separate locks.

## Decision

Add a proto-backed per-slot active-state surface, plus a runtime future and a push-delivery poller mirroring ADR-0064's shape.

- **Proto (`crates/magnetar-proto/src/consumer.rs`).** `ConsumerState` gains `is_active: Option<bool>` (last broker-reported state, `None` until the first `CommandActiveConsumerChange`), `active_changes: VecDeque<bool>` (bounded FIFO, capped at `ACTIVE_CHANGES_CAP = 32`, oldest dropped on overflow — a Failover flip happens at most a handful of times per session; the cap exists only to bound memory against a pathological broker), and `active_change_wakers: Slab<Waker>`. Four methods mirror the `receive_wakers` family exactly: `record_active_change(active)` sets `is_active`, pushes the ring (capped), and drains + wakes every parked waker; `pop_active_change()` pops the ring front; `register_active_change_waker` / `cancel_active_change_waker` manage the slab. `ConsumerState::close()` also drains + wakes the active-change slab (mirroring its existing `wake_receivers()` call) so a `next_active_change()` future already parked when the consumer closes resolves promptly instead of hanging forever; `Connection::fail_consumer_subscribe` and `Connection::fail_all_pending` do the same for their respective terminal paths, for the identical reason.
- **`conn.rs` `ActiveConsumerChange` arm.** `record_active_change(active)` and the #307 reflow predicate now read under **one** per-slot lock acquisition (previously the predicate alone held the lock); the guard is dropped before `initial_flow` re-acquires it (ADR-0038 lock ordering unchanged). Recording happens unconditionally — independent of the reflow gate's `paused` / `closed` / `pending_seek` / `flow_on_subscribe_ack` checks — because `is_active` tracks the broker's report, not local flow-control eligibility. New accessor `Connection::consumer_is_active(handle) -> Option<bool>` plus the `register_consumer_active_change_waker` / `cancel_consumer_active_change_waker` / `pop_consumer_active_change` wrappers mirror the receive-waker accessor family.
- **Drivers.** Both `magnetar-runtime-tokio` and `magnetar-runtime-moonpool` drivers admit `ConnectionEvent::ActiveConsumerChanged` into their `poll_event_if` silent-consume allow-list (alongside `ChecksumMismatch`) and drop it with an empty match arm — the real state lives in the per-slot ring the proto layer already fed directly; this drain only stops the event from piling up unbounded in the proto queue, which nothing else polls.
- **Runtime futures (both engines, mirrored).** `Consumer::is_active(&self) -> Option<bool>` is a per-slot lock read. `Consumer::next_active_change(&self)` returns a future (`ActiveChangeFut`, a 1:1 mirror of each engine's `ReceiveFut` minus the PIP-4 decrypt loop): pop the ring, and if empty check `consumer_handle_is_terminal` (issue #299's recoverable-vs-terminal distinction) before parking a waker. `Drop` cancels the waker slot, exactly like `ReceiveFut`.
- **`ConsumerApi` trait.** `is_active` and `next_active_change` are declared in the same style as `receive` (`Pin<Box<dyn Future<...> + Send + '_>>`); both engine impls delegate to the concrete type's methods.
- **Façade push surface (`crates/magnetar/src/consumer_listener.rs`).** `ConsumerEvent { BecameActive, BecameInactive }`, `ConsumerEventListener = Arc<dyn Fn(ConsumerEvent) + Send + Sync>`, `ConsumerEventListenerHandle` (`Drop`-abort `JoinHandle` wrapper with `is_running()` / async `close()`, structurally identical to `MessageListenerHandle`), and `spawn_consumer_event_listener<C: ConsumerApi + Clone>(consumer, listener)` — a `tokio::spawn`ed `loop { match next_active_change().await { Ok(a) => callback; Err(_) => break } }`. No channel (ADR-0003), no extra lock (ADR-0038 — the loop takes only what `next_active_change()` already takes), no host-clock read (ADR-0011). The callback runs **only** from this detached poller task, never under any lock.
- **Builder surface (`ConsumerBuilder`).** `event_listener: Option<ConsumerEventListener>` field, `consumer_event_listener(...)` setter, `subscribe_with_event_listener()` (same bounds as `subscribe_with_listener`) that subscribes then spawns the poller, and a `#[doc(hidden)]` `has_event_listener_for_test()` seam. Each `subscribe_with_*` terminal attaches only its own listener kind — `subscribe()` and `subscribe_with_listener()` both ignore a configured `event_listener`, mirroring how `subscribe()` already ignores `message_listener`. A caller wanting both a message listener and a consumer event listener on the same consumer subscribes once (pull-mode), clones the consumer, and passes one clone to each of `spawn_message_listener` / `spawn_consumer_event_listener` directly.

## Consequences

- **Easier.** `Consumer::is_active()` answers "am I active right now?" synchronously; `ConsumerEventListener` gives idiomatic push notification matching the Java client, learnable from the `messageListener` precedent.
- **Cost.** Three new `ConsumerState` fields (bounded — `ACTIVE_CHANGES_CAP = 32` caps the ring), one lock-scope merge in the `ActiveConsumerChange` arm (no new lock acquisition — the reflow predicate already took the per-slot lock), a new future type per engine, one `tokio::spawn`ed task per attached listener.
- **Not scoped**: `partitionId` from Java's `becameActive(Consumer, int)` — magnetar's `ConsumerEvent` carries no partition argument (single-topic consumers only; a partitioned consumer's per-partition listener is attached per child, so the partition is already implicit in which consumer's listener fired). Extending this to the wrapper consumers (`MultiTopicsConsumer` / `PartitionedConsumer` / `PatternConsumer`), the way ADR-0064 later gained a wrapper-surface extension, is a natural follow-up but out of scope here — no wrapper builder currently exposes `consumer_event_listener`.
- **Incidental fix**: `ConnectionEvent::ActiveConsumerChanged` previously accumulated unbounded in the proto event queue (neither driver drained it). It is now silently consumed like `ChecksumMismatch`, closing that leak regardless of whether any consumer attaches a `ConsumerEventListener`.
